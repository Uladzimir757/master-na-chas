# Архитектурные решения — «мастер на час»

Дата: 2026-09-03

## Отдельный проект, не слияние с Garage System

Общий переиспользуемый элемент — сама модель слот-движка (tenant/provider/
service/booking), не общий репозиторий/деплой. Причины: разный темп (этот
проект должен приносить деньги в ближайшие недели, Garage System — горизонт
8-10 мес.), разная судьба (Garage System может закрыться по условию "20
платящих клиентов к концу срока"). Если позже появится реальная причина —
сведём вручную, не проектируем эту возможность заранее.

## Не через Setmore — сразу своя платформа

Решено строить свою платформу с самого начала, без промежуточного этапа на
готовом сервисе бронирования.

## Мультитенантность — не строим

Один tenant (жёстко зашит, id известен заранее). Регистрация мастеров — через
суперадмина (создаёт аккаунт вручную), без публичной саморегистрации. Колонка
`tenant_id` в схеме оставлена (дёшево держать на будущее), но никакой логики
переключения/изоляции тенантов не пишем, пока не появится второй реальный
tenant.

## Фронтенд и мобильное приложение

Перед тем как предлагать вариант, посмотрел реальный код Garage System
(`D:\Servis_SaaS\garage`). Там есть проверенный, работающий паттерн:

- Сайт — Jinja2 + HTMX, серверный рендеринг, без отдельной сборки/фреймворка
  (`app/ui/templates/public/*`; пример — многошаговый визард бронирования:
  выбор услуги → календарь дня, HTMX-partial на `hx-get` → слоты → подтверждение)
- «Мобильное приложение» — НЕ настоящий installable PWA (`manifest.json`/
  service worker для установки не найдены). Вместо этого — Capacitor-обёртка
  (`mobile/garage-public-app`), которая просто грузит в WebView живой сайт
  (`capacitor.config.json` → `server.url` = боевой домен, `/help`). Реальной
  отдельной фронтенд-логики в этой папке нет — там дефолтный шаблон Vite,
  не используется. Настроен пока только Android (папки `ios/` нет).
- Push-уведомления мастеру уже работают в проде (pywebpush + VAPID,
  подтверждено логами: доставка id=22, задержка 2.6с). Реализация —
  ~30 строк (`WebPushSenderService.send()`).

**Первая версия этого решения (пересмотрена):** предлагал повторить рецепт
Garage System один в один (Jinja2+HTMX), аргумент — не учить второй
фронтенд-стек. Аргумент оказался слабым: ты и так не знаешь ни один стек
глубоко, второй выучить поверхностно не проблема.

**Итоговое решение: React/Next.js.** Более весомый довод, который раньше не
проговорил в цифрах: `api/slot_engine_api.py` уже отдаёт JSON
(`GET /api/availability`, `POST /api/bookings` и т.д.) — это ровно то, что
естественно потребляет React/Next.js (запрос → JSON → рендер), без
переделок. HTMX, наоборот, ждёт готовые HTML-фрагменты с сервера (как
`/booking/slots` у Garage System) — выбери мы HTMX, уже сделанный API
пришлось бы не использовать как есть, а дополнять отдельными
HTML-роутами. Цена решения — придётся завести сборку/npm (Next.js), которых
в Garage System нет, но она не идёт вразрез с уже вложенной работой, а
продолжает её.

Capacitor-обёртка под Android — тот же рецепт, что в Garage System, просто
указывает на задеплоенный Next.js-сайт вместо Jinja2-страницы. Ничего в этой
части не меняется от выбора фронтенд-стека.

## Отличие от модели данных Garage System

У Garage System трёхуровневая иерархия `tenant → station (физическая точка) →
master`. Для «мастер на час» уровень `station` не нужен — нет физических
точек, два мастера работают из дома/выезда. Схема упрощена до
`tenant → provider → service` (уже реализовано в `db/schema.sql`).

**ID:** Garage System использует integer PK (autoincrement), в моей схеме —
UUID. Оставляю UUID осознанно: если проекты когда-нибудь всё же сведём
вместе, UUID не столкнутся друг с другом при объединении данных, а int PK из
двух независимых баз — столкнутся гарантированно. Это единственное
расхождение с конвенцией Garage System, и оно намеренное, не забывчивость.

Также в Garage System алгоритм слотов устроен иначе: отдельный класс
`SlotSearchEngine.find_first_available()`, вызываемый в цикле («найди
следующий свободный слот после X», пошагово). У меня в
`compute_available_slots()` — генерация всех кандидатов за диапазон дат
разом и фильтрация занятых. Оба подхода рабочие; для объёма в 2 мастера
разница не будет заметна. Не переписываю под их вариант — но если после
запуска захочешь единообразия между проектами, это тот момент, где можно
пересмотреть.
