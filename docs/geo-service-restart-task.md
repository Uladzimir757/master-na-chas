# Задание: восстановление фонового geo-сервиса после убийства процесса (Android)

Контекст — `mobile-app-handoff.md`, раздел «Известные ограничения», пункт 1.

## Проблема

`@capgo/background-geolocation` при первом `onStartCommand` ещё не успевает
сохранить свои настройки и возвращает `START_NOT_STICKY` — Android не
перезапускает сервис сам после принудительного убийства процесса (например,
свайп из «недавних»). Пока приложение просто свёрнуто (экран выключен,
процесс жив) — всё работает, проблема только после реального kill.

## Решение (вариант 3 — не трогаем сам плагин/патч)

Доп. защита на уровне приложения, не зависящая от внутренностей плагина:

1. **`BOOT_COMPLETED`-ресивер** (Android): после перезагрузки телефона, если
   у мастера `share_location = true` (или локальный флаг «должен делиться
   геолокацией» сохранён в SharedPreferences/нативном хранилище) — заново
   стартовать плагин геолокации.
2. **Проверка при открытии кабинета**: при открытии `/cabinet/` в WebView,
   если тумблер «делюсь геолокацией» включён на сервере/локально — спросить
   у плагина, активен ли он сейчас (API плагина для статуса, если есть; иначе
   — завести свой флаг «сервис должен быть запущен», сверяемый при
   `appStateChange`/`resume`), и если нет — перезапустить тем же кодом, что
   и при обычном включении тумблера.
3. Не чинить сам плагин (patch-package/issue) в рамках этой задачи — только
   эти два внешних триггера восстановления.

## Что нужно проверить живьём

- Жёстко убить процесс через «недавние» → свайп → открыть приложение снова →
  геоточки должны возобновиться (раньше — не возобновлялись).
- Перезагрузка телефона с включённым тумблером → после загрузки (без
  открытия приложения) — сервис должен сам подняться по `BOOT_COMPLETED`.
- Обычный сценарий (просто свернуть, не убивать) — не должен сломаться
  (регрессия).

## Не входит в эту задачу

- Патч самого плагина (`START_STICKY`) — отдельная задача, если понадобится.
- iOS — там другая модель фонового выполнения, этого бага там нет
  (отдельно не трогаем).
