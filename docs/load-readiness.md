# Подготовка к нагрузке: этап проверки спроса (100–200 пользователей)

Задание от 11.11.2026. Цель — этап проверки спроса, до 100–200 пользователей
всего (не 1000 одновременно). Платные апгрейды (Render Starter, больший Neon) —
решение пользователя ≈14–16.11.2026; до этого всё в рамках бесплатных тарифов.

## Как было (11.11.2026)

- Фронтенд `master-na-chas-web` — статика на CDN Render, нагрузка не проблема.
- API `master-na-chas-api` — Render free, Франкфурт, 0.15 CPU / 512 МБ, uvicorn
  в один процесс, засыпает после 15 минут простоя (холодный старт 30–50 с).
- База Neon `master-na-chas` (`misty-rain-50153843`) — `us-east-1`, 0.25 CU,
  Postgres 18. API уже ходил в неё через пулер (`-pooler`).

## Замеры

Сценарий (`scripts/loadtest.py`): `/api/translations` → `/api/cities` →
`/api/providers?city=` → услуги мастера → слоты на неделю, без создания брони,
пауза ~1 с между шагами. API запускался **локально** (полноценный CPU, один
процесс uvicorn) против одноразовых веток Neon, не прода. Поэтому замер
показывает вклад задержки до базы и числа обращений к ней, но не потолок
CPU Render — его оценка отдельно ниже.

Задержка одного запроса к базе (SELECT 1): с машины пользователя (Польша) до
`us-east-1` — 131 мс, до `eu-central-1` — 37 мс. С Render (Франкфурт) до
`eu-central-1` — порядка 1–3 мс, то есть в проде выигрыш ещё больше, чем в

### Потолок CPU на Render free

Процессорное время локального API на смешанный поток запросов —
~10 мс на запрос (12.9 CPU-с на 1230 запросов при 30 VU). На 0.15 CPU это
потолок порядка **14 запросов в секунду**. Сценарий с 30 «активными сейчас»
пользователями даёт ~30 RPS. Для 100–200 пользователей ЗА ВЕСЬ ЭТАП (а не
одновременно) — реально единицы–десятки одновременно, то есть free-план на
грани; Starter (0.5 CPU) даёт ~3× запаса.

## Что сделано

1. **Перенос базы в EU** — новый бесплатный проект Neon `master-na-chas-eu`
   (`fancy-bar-89779562`, `aws-eu-central-1`, Postgres 18, 0.25 CU).
   Репетиция: `pg_dump` прода (только чтение) → `pg_restore` в EU-проект,
   сверка `scripts/compare_dbs.py` — все 18 таблиц совпали по числу строк,
   `btree_gist`, `pgcrypto` и EXCLUDE-констрейнт брони на месте. pytest
   (341 тест) прогнан против одноразовой ветки EU-проекта — зелёный.
   **Переключение `DATABASE_URL` на Render — отдельный шаг, см. ниже.**
2. **Кэш публичного каталога** (`app/public_cache.py`): города, мастера
   города, услуги мастера — в памяти на `PUBLIC_CACHE_SECONDS` (60 с) +
   `Cache-Control: public, max-age=60`. Сбрасывается после любой записи в
   кабинете мастера, админке и отзывах (кроме пинга геолокации и «занят»).
   Слоты НЕ кэшируются. `/api/translations` и так отдавался из памяти.
3. **Слоты и пул**: запросы на рабочие часы/исключения/брони/блоки и так шли
   одним запросом на диапазон дат, не по дню; проверка «мастер оказывает
   услугу» и её длительность слиты в один запрос (9 → 8 SQL на вызов). Пул
   SQLAlchemy настраивается `DB_POOL_SIZE` / `DB_MAX_OVERFLOW` (по умолчанию
   10 + 10, было 5 + 10). Пулер Neon уже использовался и совместим: брони не
   используют сессионных `SET` и advisory-блокировок, prepared statements
   пулер Neon поддерживает.
4. **Пингер против сна — пропущен.** Бесплатные 750 часов Render общие на
   workspace, а там активны 4 бесплатных веб-сервиса (`master-na-chas-api`,
   `zlecai-api`, `ai-homework-tutor`, `ai-homework-tutor-docker`). Держать
   наш API 24/7 — ~744 ч, остальные остались бы без часов и были бы
   приостановлены до конца месяца. Решается переходом на Starter.
5. **Мониторинг**: каждый ответ API несёт `Server-Timing: app;dur=<мс>`;
   запросы дольше `SLOW_REQUEST_MS` (1000 мс) логируются как
   `slow_request <метод> <шаблон маршрута> <статус> <мс>` — в логах Render
   видно, какой эндпоинт тормозит.

## Переключение на EU-базу (окно ~5 минут)

1. Финальный `pg_dump` прода → пересоздать схему `public` в EU-проекте →
   `pg_restore` → `scripts/compare_dbs.py` (должно быть MATCH).
2. В Render у `master-na-chas-api` заменить `DATABASE_URL` на EU-строку с
   `-pooler` (обновление переменных объединяется с остальными —
   `TICK_SECRET` и прочие не теряются) → автодеплой.
3. После `live`: смоук (`/api/cities`, мастера, слоты), повторный
   `compare_dbs` старой и новой базы — если в окно на старую успела уйти
   запись (новая бронь), перенести её руками.
4. Локальный `.env` переключить на EU-строку.
5. Старый проект `master-na-chas` (us-east-1) **не удалять минимум неделю**
   (откат = вернуть старый `DATABASE_URL`). Удаление — только по явной
   просьбе пользователя.

Одноразовые ветки для замеров (не удалять без вопроса пользователю):
`loadtest-before-2026-11-11` (старый проект), `pytest-rehearsal-2026-11-11` и
`loadtest-eu-2026-11-11` (EU-проект).

## Платное — подготовлено, не включено (решение ≈14–16.11.2026)

**Render API free → Starter** (меняет пользователь в дашборде):
1. Start command: `uvicorn app.main:app --host 0.0.0.0 --port $PORT --workers 2`
   (на 512 МБ: процесс ~170 МБ, 2 воркера ≈ 350 МБ; 3–4 — только если
   память позволит по метрикам).
2. Соединения: воркеры × (`DB_POOL_SIZE` + `DB_MAX_OVERFLOW`) = 2 × 20 = 40
   клиентских соединений к пулеру Neon — в пределах лимитов (пулер держит
   тысячи клиентских соединений, к самой базе он ходит своим пулом).
3. Таймер подтверждения: env `TICK_SECRET` + Render Cron Job раз в минуту
   `POST /internal/tick` с заголовком `X-Tick-Secret` (см. CLAUDE.md).
4. Кэш каталога на воркер свой — после правки мастера другие воркеры
   досчитают старое не дольше 60 с (`PUBLIC_CACHE_SECONDS`).

**Neon**: в EU-проекте поднять максимум автомасштабирования до 1–2 CU,
минимум оставить 0.25 (`autoscaling_limit_max_cu`) — платится только за
использованное.

После каждого шага: Render `http_latency` p95, CPU, память; повторить
`scripts/loadtest.py` против прода только в тихое время и только чтением.
