# MVP-техзадание: слот-движок и API «мастер на час»

Цель этого этапа: рабочий API бронирования, проверяемый через curl (Postman
не нужен — упомянул его раньше как опциональную GUI-альтернативу, но для
проверки этих 4 эндпоинтов достаточно голого curl, без лишнего инструмента),
без единого экрана интерфейса. Интерфейс — следующий этап, поверх уже
работающего бэкенда. Контекст решений — см. `decisions.md`.

## Что уже есть (не переписывать с нуля)

- `db/schema.sql` — применена и проверена на реальном Postgres 16
  (EXCLUDE constraint против двойного бронирования подтверждён рабочим
  тестом: пересекающаяся бронь того же мастера реально отклоняется, отмена
  освобождает слот обратно)
- `api/slot_engine_api.py` — каркас FastAPI + SQLAlchemy 2.0 async:
  `GET /api/availability`, `POST /api/bookings`, `GET /api/bookings`,
  `PATCH /api/bookings/{id}/status`. Синтаксис проверен (`py_compile`), но
  без реальной сессии БД не запускался.

## Что нужно доделать в этом этапе

### 1. Подключение к БД

`get_db()` в `slot_engine_api.py` сейчас — `NotImplementedError`. Поднять
отдельную Neon-базу под этот проект (не общую с Garage System — отдельные
проекты, см. `decisions.md`), применить `schema.sql`, написать реальный
`async_sessionmaker`/`get_db()`. Можно посмотреть, как это устроено в Garage
System, для ориентира — но реализовать в этом репозитории самостоятельно, не
импортом из чужого проекта.

### 2. Сидинг одного tenant + двух provider

Один tenant (жёстко), два provider (ты + друг) — вставить вручную или
одноразовым скриптом, не через публичную форму регистрации (решение:
регистрация мастеров — только через суперадмина, см. `decisions.md`).

### 3. «Любой доступный мастер» в /api/availability

В Garage System есть полезный паттерн: клиент может выбрать конкретного
мастера ИЛИ «любой доступный» (`PublicBookingService.normalize_master_preference`,
`master_preference: auto | specific`). Добавить то же в
`GET /api/availability`: если `provider_id` не передан, а передан только
`service_id` — вернуть слоты по всем provider, которые умеют эту услугу
(таблица `provider_service`), с пометкой, какому provider принадлежит
каждый слот.

### 4. Простая авторизация для мастеров

Полноценный account-management не нужен — это минимум под текущий масштаб
(2 мастера), не финальная архитектура. Если пойдёт развитие (больше
мастеров, нужны роли/права) — дорабатываем тогда, не сейчас. Минимум:
таблица `master_user` (`provider_id`, `email`, `password_hash`,
`telegram_chat_id` nullable — заполняется потоком из п.5, не руками),
сессионная авторизация (cookie — для двух пользователей JWT избыточен).
Суперадмин создаёт запись вручную
(скрипт или простой закрытый `/admin`, доступный только тебе).

### 5. Уведомление мастеру при новой брони

Никакого хардкода per-master данных (chat_id и т.п.) — это данные, а не
конфигурация, место им в БД, не в конфиг-файле/env.

- Telegram: добавить колонку `telegram_chat_id` в `master_user` (см. п.4),
  изначально `NULL`. Токен бота — это платформенный секрет, ему нормально
  жить в конфиге/env (один бот на весь проект, не per-master). Флоу привязки
  без ручного копирования id: суперадмин генерирует мастеру персональную
  deep-ссылку `t.me/<bot_username>?start=<одноразовый_токен>`, токен заранее
  сохранён в БД против нужного `provider_id`/`master_user_id`. Мастер один
  раз переходит по ссылке и жмёт «Старт» — бот получает `/start
  <токен>` в апдейте, бэкенд по токену находит нужную запись и сам пишет туда
  пришедший `chat_id`. TODO перед кодом: завести бота через @BotFather,
  получить token, реализовать этот webhook/polling-обработчик `/start`.
- Web Push — переиспользовать паттерн `WebPushSenderService.send()` из
  Garage System (скопировать структуру ~30 строк, не импортировать из
  чужого репозитория; нужны свои VAPID-ключи — платформенный секрет, в
  конфиге/env, не путать с per-master push-подпиской, которая тоже хранится
  в БД, не в конфиге)

### 6. Уведомление клиенту — SMS

Сравнил по факту, не на словах (цены на 2026):

| Провайдер | Цена/SMS | Мин. пополнение | Особенность |
|---|---|---|---|
| Twilio | ~$0.0457 (≈0,19–0,20 zł) | нет, pay-as-you-go | Alphanumeric Sender ID — 0 zł/мес, только исходящие (нам входящие и не нужны); отдельный номер — $4/мес, если позже понадобится приём ответов |
| SMSAPI.pl | 0,17 zł (от 49 zł) → 0,11 zł (от 10k zł) | 49 zł | Польский провайдер; требования к аккаунту (нужна ли фирма/NIP для полноценного использования) не проверял — 5 минут на их сайте, если станет актуально |
| SerwerSMS.pl | 0,19 zł (от 50 zł) → 0,10 zł (от 10k zł) | 50 zł, деньги сгорают через 3 мес | Профиль похож на SMSAPI |

При ожидаемом объёме ~20–40 SMS/мес (см. расчёт заказов) разница в цене
между всеми тремя — единицы злотых в месяц, не решающий фактор.

**Решение: Twilio, реализуем сейчас, не заглушкой.** Причина — не цена, а
то, что его можно подключить прямо сегодня: Alphanumeric Sender ID
регистрируется без привязки к польской фирме/NIP, а у тебя именно это сейчас
не закрыто (JDG недоступен, spółka не зарегистрирована). Польские провайдеры
почти наверняка рассчитаны на B2B-аккаунт с данными фирмы — откладывать
реальные SMS-уведомления до момента, когда spółka будет готова, при наличии
рабочей глобальной альтернативы смысла нет. После регистрации spółka имеет
смысл пересчитать в сторону SMSAPI/SerwerSMS — дешевле на объёме и звучит
«локальнее» для клиента (свой sender ID на польском).

**Что делать в рамках этого этапа:**
- Завести Twilio-аккаунт, зарегистрировать Alphanumeric Sender ID (до 11
  латинских символов — например название бренда)
- В `POST /api/bookings`: после успешного создания брони — реальный вызов
  Twilio REST API (`twilio` python-пакет, `messages.create`) на
  `client_phone` с текстом подтверждения (дата/время/услуга/мастер)
- Ошибка отправки SMS не должна ронять сам `POST /api/bookings` — бронь
  создаётся в любом случае, отправка SMS — best-effort с логированием сбоя,
  не часть транзакции создания брони

## Сразу после этого этапа

Это не «когда-нибудь потом» — mobile + web с самого начала было условием
(см. `decisions.md`), API-первым идёт только потому, что логику проще
проверить curl'ом, а не потому что мобильная часть под вопросом. Прямо
следом за этим этапом, без паузы:

- Интерфейс — React/Next.js, потребляет уже готовый JSON API
  (`api/slot_engine_api.py`) как есть, без переделки под HTML-фрагменты
  (решение пересмотрено — см. `decisions.md`, раздел «Фронтенд и мобильное
  приложение»)
- Capacitor-обёртка под Android — тем же рецептом, что в Garage System
  (`server.url` на боевой домен, никакой отдельной фронтенд-логики), только
  указывает на задеплоенный Next.js-сайт. Технически ей действительно нужен
  готовый веб-интерфейс, чтобы было что грузить в WebView — но она следующий
  шаг сразу после него, а не отложенная на неопределённый срок идея.

## Явно вне скоупа (сюда не идём вообще, не «пока»)

- Мультитенантность, публичная саморегистрация
- iOS
- Что-либо про Garage System — этот репозиторий его не трогает и от него не
  зависит

## Проверка перед переходом к интерфейсу

- [ ] Схема применена на реальной (Neon) БД, не только локально
- [ ] curl-сценарий: получить доступные слоты → создать бронь → повторный
      запрос на то же время отклоняется 409 → отменить бронь → тот же слот
      снова доступен
- [ ] Сообщение в Telegram реально приходит мастеру при новой брони
- [ ] Web Push реально приходит (аналогично тому, как проверено в Garage
      System — id доставки, задержка)
- [ ] SMS через Twilio реально приходит клиенту на польский номер при
      создании брони
